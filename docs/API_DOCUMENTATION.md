# VELoop CAPTCHA Earn API Documentation

## 1. Overview

The VELoop CAPTCHA Earn module exposes authenticated REST APIs for account access, CAPTCHA challenge generation, server-side verification, reward claiming, challenge skipping, wallet balance, wallet transaction history, and CAPTCHA history.

The backend is the source of truth for:

- CAPTCHA correctness
- Challenge ownership and validity
- Challenge expiry and completion state
- Reward amount
- Wallet balance
- Reward transactions
- Claim eligibility

The frontend never supplies or controls the authoritative `userId`, `correctOption`, wallet balance, or reward amount.

## 2. Base URL

### Local development

```text
http://localhost:5001/api
```

For a deployed environment, replace the host with the deployed backend URL.

## 3. Authentication

Protected endpoints require a JWT access token returned by the authentication APIs.

```http
Authorization: Bearer <JWT_TOKEN>
```

JWT tokens are generated by the backend and expire after 7 days.

## 4. Standard Response Format

Successful JSON responses use a structure similar to:

```json
{
  "success": true,
  "message": "Operation completed successfully",
  "data": {}
}
```

Error responses use a structure similar to:

```json
{
  "success": false,
  "code": "ERROR_CODE",
  "message": "Human-readable error message"
}
```

Some successful endpoints return domain-specific top-level fields such as `token`, `reward`, `wallet`, or `history`.

# 5. Authentication APIs

## 5.1 Register

### `POST /api/auth/register`

Creates a new candidate/user account.

**Authentication:** Not required.

### Request

```json
{
  "name": "Ashu",
  "email": "ashu@example.com",
  "password": "your-password"
}
```

### Validation

- `name` is required and must be 2-50 characters.
- `email` must be valid.
- `password` must be 8-128 characters.
- Email is normalized to lowercase before storage.
- Duplicate email addresses are rejected.

### Success — `201 Created`

```json
{
  "success": true,
  "message": "Registration successful",
  "token": "<JWT_TOKEN>",
  "user": {
    "id": "<USER_ID>",
    "name": "Ashu",
    "email": "ashu@example.com"
  }
}
```

### Common errors

| Status | Code / Condition | Meaning |
|---|---|---|
| 400 | Validation error | Invalid/missing name, email, or password |
| 409 | Duplicate email | Email already registered |
| 500 | Server error | Unexpected backend failure |

# 6. CAPTCHA APIs

## 6.1 Generate a New CAPTCHA Challenge

### `GET /api/captcha/generate`

Creates a new server-side CAPTCHA challenge for the authenticated user. Any previously active challenge for that user is invalidated.

**Authentication:** Required.

### Request

No request body.

```http
GET /api/captcha/generate
Authorization: Bearer <JWT_TOKEN>
```

### Success — `201 Created`

```json
{
  "success": true,
  "message": "CAPTCHA challenge generated successfully",
  "data": {
    "challengeId": "<CHALLENGE_ID>",
    "options": [
      "A7K2P9",
      "AJK29P",
      "A7L9P2",
      "X4M8Q1"
    ],
    "expiresAt": "2026-10-02T03:30:00.000Z"
  }
}
```

The public response contains the challenge ID, four options, and expiry. The server-side `correctOption` is not returned.

### Common errors

| Status | Code | Meaning |
|---|---|---|
| 401 | `AUTHENTICATION_REQUIRED` | No authenticated user |
| 500 | `INTERNAL_SERVER_ERROR` | Unable to generate challenge |

---

## 6.2 Get CAPTCHA Image

### `GET /api/captcha/image/:challengeId`

Returns the visual CAPTCHA image for the authenticated user's active challenge.

**Authentication:** Required.

### Example

```http
GET /api/captcha/image/<CHALLENGE_ID>
Authorization: Bearer <JWT_TOKEN>
```

### Success — `200 OK`

```text
Content-Type: image/svg+xml
```

The response body is the generated SVG image.

### Common errors

| Status | Meaning |
|---|---|
| 400 | Missing/invalid challenge ID |
| 401 | Authentication required |
| 404 | Challenge not found |
| 409 | Challenge already completed/inactive |
| 410 | Challenge expired |
| 500 | Server error |

## 6.3 Submit / Verify CAPTCHA

### `POST /api/captcha/submit`

Verifies the selected option on the server and determines the reward from backend configuration.

**Authentication:** Required.

### Request

```json
{
  "challengeId": "<CHALLENGE_ID>",
  "selectedOption": "A7K2P9"
}
```

### Validation and security rules

- Both `challengeId` and `selectedOption` are required.
- The selected option must be one of the four options issued for that challenge.
- The challenge must belong to the authenticated user.
- The challenge must still be active.
- Expired challenges are rejected.
- A challenge can be verified only once.
- Client-supplied `reward`, `rewardAmount`, `isCorrect`, or `userId` values are ignored for authoritative processing.
- The backend compares the submitted option against its stored `correctOption`.

### Success — `200 OK`

```json
{
  "success": true,
  "code": "CAPTCHA_VERIFIED",
  "correct": true,
  "result": "CORRECT",
  "message": "CAPTCHA verified successfully",
  "reward": {
    "currency": "GEMS",
    "amount": 1
  },
  "challengeId": "<CHALLENGE_ID>",
  "claimAvailable": true
}
```

For an incorrect but valid option, the same response structure is returned with:

```json
{
  "correct": false,
  "result": "WRONG",
  "reward": {
    "currency": "GEMS",
    "amount": 0.5
  }
}
```

### Common errors

| Status | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Missing request field |
| 400 | `INVALID_OPTION` | Selected value was not one of the four issued options |
| 401 | Authentication required | Missing/invalid authentication |
| 404 | `CHALLENGE_NOT_FOUND` | Challenge does not belong to the authenticated user or does not exist |
| 409 | `CHALLENGE_ALREADY_COMPLETED` | Challenge was already consumed |
| 410 | `CHALLENGE_EXPIRED` | Challenge expired before verification |
| 500 | `INTERNAL_SERVER_ERROR` | Unexpected backend failure |

---

## 6.4 Claim CAPTCHA Reward

### `POST /api/captcha/claim`

Claims a verified reward and credits the server-side wallet.

**Authentication:** Required.

### Request

```json
{
  "challengeId": "<CHALLENGE_ID>"
}
```

### Processing

The backend atomically:

1. Reserves the pending reward for the completed challenge.
2. Updates the user's wallet.
3. Creates a `GemTransaction` ledger record.
4. Marks the challenge reward as claimed.
5. Records an audit event.

### Success — `200 OK`

```json
{
  "success": true,
  "code": "REWARD_CLAIMED",
  "message": "Reward claimed successfully",
  "reward": {
    "currency": "GEMS",
    "amount": 1
  },
  "wallet": {
    "gems": 1
  },
  "challengeId": "<CHALLENGE_ID>"
}
```

### Common errors

| Status | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Missing challenge ID |
| 401 | Authentication required | Missing/invalid authentication |
| 404 | `CHALLENGE_NOT_FOUND` | Challenge does not exist for the authenticated user |
| 409 | `REWARD_ALREADY_CLAIMED` | Same reward was already claimed |
| 409 | `CLAIM_NOT_AVAILABLE` / `NO_REWARD_AVAILABLE` | Challenge is not eligible for a claim |
| 500 | `INTERNAL_SERVER_ERROR` | Unexpected backend failure |

## 6.5 Skip / No Thanks

### `POST /api/captcha/skip`

Skips the current challenge without crediting its reward and then allows the client to request another challenge.

**Authentication:** Required.

### Request

```json
{
  "challengeId": "<CHALLENGE_ID>"
}
```

### Success — `200 OK`

```json
{
  "success": true,
  "code": "CAPTCHA_SKIPPED",
  "message": "CAPTCHA skipped successfully",
  "challengeId": "<CHALLENGE_ID>",
  "status": "skipped"
}
```

### Common errors

| Status | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Missing challenge ID |
| 401 | Authentication required | Missing/invalid authentication |
| 404 | `CHALLENGE_NOT_FOUND` | Challenge is unavailable for this user |
| 409 | Conflict | Challenge cannot be skipped in its current state |
| 500 | `INTERNAL_SERVER_ERROR` | Unexpected backend failure |

## 6.6 CAPTCHA History

### `GET /api/captcha/history`

Returns the authenticated user's CAPTCHA activity.

**Authentication:** Required.

### Query parameter

```text
limit=20
```

The backend accepts a positive integer and caps the returned history to 100 records.

### Example

```http
GET /api/captcha/history?limit=20
Authorization: Bearer <JWT_TOKEN>
```

### Success — `200 OK`

```json
{
  "success": true,
  "data": {
    "history": [
      {
        "challengeId": "<CHALLENGE_ID>",
        "result": "correct",
        "rewardAmount": 1,
        "rewardStatus": "claimed",
        "status": "completed",
        "createdAt": "2026-10-02T03:20:00.000Z",
        "completedAt": "2026-10-02T03:20:20.000Z"
      }
    ],
    "count": 1
  }
}
```

### Security note

`correctOption` is intentionally excluded from history responses.

### Common errors

| Status | Meaning |
|---|---|
| 400 | Invalid query/request values |
| 401 | Authentication required |
| 500 | Server error |

# 7. Wallet APIs

## 7.1 Get Gem Balance

### `GET /api/wallet/gems`

Returns the current server-side Gem balance for the authenticated user.

**Authentication:** Required.

### Example

```http
GET /api/wallet/gems
Authorization: Bearer <JWT_TOKEN>
```

### Success — `200 OK`

```json
{
  "success": true,
  "data": {
    "gems": 1
  }
}
```

The frontend uses this endpoint after login, after claiming a reward, and after page refresh. The authoritative wallet value is stored in MongoDB rather than browser storage.

### Common errors

| Status | Meaning |
|---|---|
| 401 | Authentication required |
| 500 | Unable to fetch wallet balance |

---

## 7.2 Get Wallet Transactions

### `GET /api/wallet/transactions`

Returns the authenticated user's Gem reward transaction ledger.

**Authentication:** Required.

### Query parameter

```text
limit=20
```

### Example

```http
GET /api/wallet/transactions?limit=20
Authorization: Bearer <JWT_TOKEN>
```

### Response

The frontend consumes the transaction list from `data.transactions`. Each reward transaction is associated with its challenge through `referenceId`.

Example shape:

```json
{
  "success": true,
  "data": {
    "transactions": [
      {
        "transactionId": "<TRANSACTION_ID>",
        "userId": "<USER_ID>",
        "currency": "GEM",
        "amount": 1,
        "type": "CAPTCHA_REWARD",
        "source": "CAPTCHA_EARN",
        "referenceId": "<CHALLENGE_ID>",
        "balanceBefore": 0,
        "balanceAfter": 1,
        "status": "COMPLETED",
        "createdAt": "2026-10-02T03:21:00.000Z"
      }
    ],
    "count": 1
  }
}
```

# 9. Reward Configuration

The reward values are controlled on the backend through the reward configuration model.

Current development configuration:

```text
Correct CAPTCHA reward: +1 GEM
Wrong CAPTCHA reward:   +0.5 GEM
Currency:                GEM
```

The reward configuration is not accepted from the client request and is not used as a frontend authority.

# 10. Security and Replay Protection Summary

The API is designed so that the authenticated backend identity is the source of truth. Client-supplied `userId`, `isCorrect`, or reward values cannot be used to grant a forged reward.

The implementation also covers:

- JWT-protected CAPTCHA and wallet APIs
- Server-side option validation
- Server-side correct-answer comparison
- Challenge ownership checks
- Challenge expiry checks
- One-time verification state
- One-time reward claim state
- Atomic reward/wallet/ledger processing using MongoDB transactions
- Duplicate ledger protection
- Rate limiting on the `/api` surface
- Audit logging for normal and suspicious reward-related events

# 11. Endpoint Flow Used by the Frontend

```text
POST /api/auth/register       (optional for new users)
                ↓
POST /api/auth/login
                ↓
GET  /api/captcha/generate
                ↓
GET  /api/captcha/image/:challengeId
                ↓
POST /api/captcha/submit
                ↓
POST /api/captcha/claim
                ↓
GET  /api/wallet/gems
                ↓
GET  /api/wallet/transactions
                ↓
GET  /api/captcha/history
                ↓
GET  /api/captcha/generate   (next challenge)
```

For the **No Thanks** path:

```text
POST /api/captcha/submit
        ↓
POST /api/captcha/skip
        ↓
GET /api/captcha/generate
```

## 12. Assignment Endpoint Mapping

The assignment describes `current` and `new` CAPTCHA routes as a recommended API shape, while this implementation uses a single authenticated generation endpoint:

| Assignment concept | Implemented endpoint |
|---|---|
| Get current/new CAPTCHA | `GET /api/captcha/generate` |
| Verify | `POST /api/captcha/submit` |
| Claim | `POST /api/captcha/claim` |
| Skip / No Thanks | `POST /api/captcha/skip` |
| CAPTCHA image | `GET /api/captcha/image/:challengeId` |
| History | `GET /api/captcha/history` |
| Gem balance | `GET /api/wallet/gems` |
| Reward configuration | Backend-only model/config; no public `/config` endpoint |

This mapping keeps the implementation aligned with the required behavior while documenting the actual routes exposed by the application.
